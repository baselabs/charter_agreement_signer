[CAP] Charter Agreement · the Elixir companion signer

The companion signer, in Elixir.

charter_agreement_signer is what a charter party calls to produce the signatures: the protocol package generates each artifact’s deterministic RFC 7515 signing input and refuses to sign; this library takes a {module, term()} key handle whose callbacks reach your own custody — an HSM, a KMS, an in-process test key — and produces the signed compact. The private key never enters the library. One dependency: the public protocol package. Verifiers depend only on the protocol package, never on this signer.

What the companion guarantees

The custody discipline the whole family inherits — enforced here first.

Custody is the caller’s.

A signing library that touches key material becomes the most valuable target in your system.

The signer only ever calls {module, term()} callbacks into your custody — the protocol package holds no key parameter, signer callback, or custody handle at all.

It refuses before it touches the key.

Most signers will happily sign whatever claims they are handed.

The honest-signer refusals (R1–R3) reject claims the signature could not honestly cover — before sign/2 is ever called.

Nothing leaves unverified.

A custodian misconfiguration should not be discovered downstream, by the verifier.

Every path runs the shared tail with a wrong-key guard and a post-sign verification — the artifact that leaves is the artifact CAP will accept.
